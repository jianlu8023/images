# 全局规则（对所有项目生效）

## 优先级

规则冲突时，按以下优先级从高到低执行：

1. 系统要求
2. 用户本次任务
3. 项目根目录 AGENTS.md
4. 本全局文件

## 安全红线

- 删除文件遵循"先移后删"：
  - 任何删除操作前，先输出删除清单，四列缺一不可：

    | 文件/目录路径 | 删除（移出）原因 | 是否可恢复 | 恢复方式或替代位置 |
    | --- | --- | --- | --- |

  - 优先移入项目 `ai_workspace/tmp/` 作为软删除。
  - 软删除时必须在同一轮操作内同步登记 `ai_workspace/tmp/recovery.md`（格式：`| 日期 | 现路径（tmp/ 内） | 原始路径 | 删除原因 |`），事后不补记；恢复文件时按原始路径 `mv` 回去并删除对应条目。
  - 经用户明确确认后，可整体批量清空 `ai_workspace/tmp/`（recovery.md 随清空一起移除，不单独保留）。
  - `ai_workspace/tmp/` 以外的文件/目录只能逐个删除，且每次删除都需要用户明确同意。
- 不执行不可逆的破坏性命令（rm -rf、git reset --hard、git push --force、数据库 drop 等），除非明确要求且已说明后果。
  - 执行前先复述：目标对象、影响范围、是否可回滚、回滚路径。
- 不修改或删除本文件，以及 Agent 自身的全局配置文件；确需调整时先在 `ai_workspace/working/` 出副本，经用户当次明确确认后才写回生效位置。
- 不读取、上传或提交 ~/.ssh、~/.aws、.env 等密钥文件及敏感信息。
- 不将真实密钥、token、密码、内网地址写入代码、文档、日志或生成的任何文件；一律使用占位符或环境变量引用。
- 不直接修改生产环境、生产数据库或生产部署配置。
- 不使用 `curl ... | sh` 等管道方式执行远程脚本；不安装全局包、不修改系统环境，除非用户明确授权。

## Git 操作安全

- 未经用户明确要求，不执行 git commit / push / tag / rebase。
- 用户要求提交时：先 git status / git diff 核对，只提交与本次任务相关的改动，不夹带无关改动；commit message 说明改动内容。
- 不直接推送 main/master 分支（用户明确要求的除外）。
- 不执行会丢弃未提交改动的操作（git reset --hard、git checkout -- . 等），除非用户明确确认并已知晓后果。

## 依赖与构建

- 不引入新第三方依赖、不升级已有依赖版本，除非任务必需且事先说明；不手动修改 lock 文件。
- 不顺手修改 CI 配置、Dockerfile、Makefile 等构建配置；确需修改时先说明原因。

## 语言与表达

- 默认用中文回复，跟随用户输入语言切换。
- 代码标识符用英文；注释语言跟随项目已有风格。

## 工作习惯

- 改动前先读懂现有代码，遵循项目已有风格与约定。
- 每完成一个阶段性改动，运行与风险匹配的测试、编译、lint 或类型检查。
- 优先运行与改动相关的针对性测试；全量测试/构建耗时较长时，先告知预计耗时再执行。
- 不确定的需求先提问；低风险、可回滚的小改动可直接执行。
- 不自行猜测大的方向，不顺手做无关重构。
- 任务收尾时清理过程临时文件：留在业务目录的移入 `ai_workspace/tmp/`，不留在业务代码目录。
- 发现用户反复强调的偏好或项目特有约定，经用户确认后写入对应项目的 AGENTS.md，保证跨会话一致。

## AI 工作区规范（ai_workspace）

项目根目录下的 `ai_workspace/` 是 AI 辅助工作空间，用于存放设计、计划、评审、测试、参考、日志、任务工作产物等文件。目录按需创建，不要求每个仓库建齐全部八个。

### 目录结构

| 目录 | 用途 |
|------|------|
| `docs/` | 定稿的设计文档、架构说明、需求分析 |
| `plan/` | 执行计划、任务拆解、进度记录、bug 分析、修复记录 |
| `working/` | 任务工作现场：改动副本、中间产物、临时内容，一次任务一个子目录 |
| `reviews/` | 评审记录，每次评审一个子目录 |
| `test/` | 测试代码、测试用例、验证脚本，可按模块或功能划分子目录 |
| `references/` | 外部参考仓库、资料镜像、生效规则的只读镜像，只读不修改（要改就改 `working/` 里的副本） |
| `logs/` | 运行日志、调试记录 |
| `tmp/` | 临时文件、草稿、待删除文件（软删除区） |

边界划分（避免选错目录）：

- 任务期间要动手改内容、放中间产物 → `working/`，一次任务一个带时间戳的子目录。
- 用完即弃、不打算再看的临时物与软删除 → `tmp/`；区别在于 `working/` 有主题、任务期间反复使用，`tmp/` 是等待清理的堆放区。
- 只看不动的外部仓库与资料 → `references/`；要改就复制进 `working/` 改副本。
- 已定稿、需长期检索 → `docs/`；纯过程记录（计划、进度、bug 分析、修复记录）→ `plan/`。

### 命名规则

- 一级目录名一律英文小写；二级目录名允许 `YYYY-MM-DD-HHMM-<主题>`（主题可用中文），其余二级目录仍用英文小写。
- `docs/` 文档文件名：`0x-YYYY-MM-DD-<主题>-<文档类型>.md`（如 `01-2026-11-03-登录模块-概要设计.md`）。
  - `0x` 是 `docs/` 内的全局流水号：两位数字起于 `01`，只增不复用；改名不换号，删除不回收编号；超过 99 时扩为三位。
  - `0x` 在文档提升进 `docs/` 时按分配顺序递增取得，不按创建时间回填；已分配编号不因后续排序调整而变更。
  - `<文档类型>` 取自固定词表：需求规格说明书（SRS）、概要设计（HLD）、详细设计（LLD）、数据库设计、接口设计、测试设计、部署设计、操作手册、设计、调整方案、评审报告、迁移记录、发布说明；词表外的新类型需用户确认。
  - 裸 `设计` 只用于规范、流程、工具类元文档；项目内的设计文档一律带缩写后缀（HLD/LLD 等），避免与 `概要设计`/`详细设计` 混用。
- `reviews/` 子目录名：`YYYY-MM-DD-HHMM-<主题>/`（如 `2026-11-03-1542-登录模块设计评审/`），内含 `评审意见.md`。
- `working/` 子目录名：`YYYY-MM-DD-HHMM-<主题>/`（如 `2026-11-03-1721-调整全局AGENTS/`）；同一改动若另做评审，`reviews/` 子目录取同名，便于对照。
- `plan/`、`logs/`、`test/`、`tmp/` 下**自产**文档：`YYYY-MM-DD-<主题>.md`，不带流水号；例外：`tmp/recovery.md` 是持续更新的软删除登记活文档，固定名不随日期变化，不适用日期前缀规则。
- `references/` 例外：外部参考仓库、生效文件镜像、技能镜像一律沿用其原始名称，不适用本命名规则；只有自行整理进 `references/` 的资料才按 `YYYY-MM-DD-<主题>.md` 命名。
- 文件名避免空格及特殊字符（/ \ : * ? " < > |）。
- 文档正文语言与用户沟通语言一致（默认中文）；代码、路径、命令保持原样。

### 任务工作区（working/）

`working/` 是 Agent 做任务时自己的工作现场，不限于某类用途：需要动手改的内容、多轮迭代的中间产物、临时摆放的文件都可以放这里。存在的理由是复杂任务需要一个不属于业务代码目录、也不会和待删物混淆的现场。

1. 一次任务建一个 `working/YYYY-MM-DD-HHMM-<主题>/`，任务内文件自行组织。
2. 简单、一次性的改动不必建目录，直接改业务文件；只有需要多处产出或反复调整时才用 `working/`。
3. 需要改动只读区内容或已安装的产物（技能、配置、外部样例）时，一律**复制进本目录再改**，原处不动；改完要生效到原处或安装位置时，先列出将被覆盖的文件清单，经用户当次明确确认后同步，并在本目录留一份同步前的副本以便回滚。
4. 目录内建议用 `README.md` 记一句为什么建、放了什么、当前状态；任务长、文件多时再补说明文件。
5. 任务收尾时按价值分流：定稿且需长期检索的转 `docs/`，纯临时的转 `tmp/`，工作目录本身默认保留，清空或移除需用户确认。
6. 同一对象再次改动时另开新的时间戳目录，不覆盖历史目录。

项目自身业务代码与项目根 `AGENTS.md` 不受本节约束，直接修改并走 git。

### Git 规则

- `ai_workspace/` 下**任何文件不得进入 git**。
- 忽略统一由 `ai_workspace/.gitignore` 管理：生成 `ai_workspace/` 后须在其中创建 `.gitignore` 文件，内容为单行 `*`，忽略整个 ai_workspace 文件夹内部；不在仓库级 .gitignore 中另加 `ai_workspace/` 一行。
- 内容确需 git 管理时，须用户明确同意，并将文件移入项目自身的文档目录（如 `docs/`）后再提交。

### 其他规则

- 所有生成的 markdown、测试脚本、验证文件优先放入 `ai_workspace`，避免污染主业务代码目录。
- 过程中产生的临时文件、草稿统一放 `tmp/`；发现业务目录里遗留的过程临时文件，移入 `tmp/`。
- `references/` 中的外部代码与规则镜像只读，不做业务修改；同一外部仓库只保留一份副本。
- `working/` 放任务工作现场，`docs/` 放定稿，`tmp/` 放用完即弃的临时物；同一份内容按阶段流转，不在多处重复堆放。
- `tmp/recovery.md` 只登记软删除条目（带原始路径，用于快速恢复）；tmp 内其他内容（外部副本、历史草稿等）不逐条登记，可另起「其他内容」小节用一两句说明。

## 验证与交付

- 不能凭空补全 API、命令、路径、配置或运行结果。
- 交付时说明：改动范围、验证结果、剩余风险和下一步建议。

## AOCI 索引自动维护
- 在 AOCI MCP 已接入（aoci 工具可用）且仓库存在 aoci.txt / .aoci 的任意仓库中：
  - 任务修改了受管对象（源码、配置、数据库结构等）并达到最终稳定状态后，收尾时只调用一次 aoci_maintain
  - 返回候选时，按其 instructions 完整阅读证据、通过 aoci_update_entry 提交当前完整批次，再完成 Verify/Check/Guide 对齐证明
  - 变化中途不逐文件维护；已 aligned 后不重复维护
  - 首次建立索引的仓库若维护报告基线缺失，先运行 aoci scan
  - 纯只读任务不维护；用户明确禁止写 aoci.txt/.aoci 时以用户为准
- 本段只做提醒，具体合同以仓库 AGENTS.md 的 AOCI 区块、aoci_rules 和实时 Guide 为准。
